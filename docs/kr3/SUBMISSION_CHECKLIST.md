# КР №3: требования, реализация и подготовка к сдаче

Проверка и исправления: 9 ноября 2026 года. Основная сущность — заказ магазина винила; справочник — пластинка. Все обязательные функциональные разделы представлены. Два обнаруженных дефекта CSV/аудита исправлены и покрыты регрессионными тестами.

## Что требуется и что реализовано

| Требование | Что реализовано | Где показать |
|---|---|---|
| Продолжение КР1–2 | Сохранена предметная область, данные старой базы переносятся к UUID; JavaFX остаётся отдельным клиентом | `src/`, миграции V0/V5, `scripts/verify-legacy-migration.py` |
| Структура backend | controller, service, repository, domain, dto, security, filter, error, config | `backend/src/main/java/ru/mirea/vinylstore/` |
| 1. Авторизация | Пароль, BCrypt, VIEWER/MANAGER/ADMIN, короткий JWT, серверный refresh с ротацией, logout, текущий пользователь, смена пароля, обязательная замена временного, блокировка перебора | Вход, кабинет, `/api/auth/*` |
| Индивидуальное задание | Регистрация и вход по шестизначному коду на Gmail; Gmail API OAuth2, хеш кода, TTL 5 минут, однократность, лимиты отправки и попыток | Формы регистрации/входа; OAuth-настройка описана в `README.md` |
| 2. Основная сущность | UUID, номер, альбом, исполнитель, покупатель, контакты, дата, пластинка, статус, сумма, paid, количество, теги, приоритет, timestamps, version, архив | Панель → «Заказы» |
| 3. CRUD и архив | Список, карточка, создание, изменение с version, архив, восстановление, окончательное удаление ADMIN | Панель → «Заказы» |

| 9. Аналитика | Всего, активные, архивные, оплаченные, средняя сумма, группировки по пластинке/статусу/приоритету | Панель → «Аналитика» |
| 10. Пользователи | Пагинация, создание, изменение имени/email/ролей/активности, сброс временного пароля, запрет входа отключённому | Панель → «Пользователи» |
| 11. Аудит | Входы и важные изменения, пользователь/событие/сущность/UUID/время/описание, correlation ID, поиск/сортировка/страницы, доступ ADMIN; событие экспорта CSV сохраняется | Панель → «Аудит», заголовок X-Correlation-ID |

## Что нужно сделать команде перед защитой

- [ ] На компьютере защиты установить и запустить Docker Desktop; распаковать архив и выполнить `bash scripts/start-kr3.sh` либо `powershell -ExecutionPolicy Bypass -File scripts/start-kr3.ps1`. Скриптам нужен Python 3. Для просмотра кода и локального Maven-запуска нужны JDK 21 и совместимый Maven.
- [ ] Проверить `http://localhost:8080/actuator/health` и три `healthy` сервиса. Перезапускать без удаления тома PostgreSQL.
- [ ] На новой базе войти администратором с реквизитами из созданного локального `.env`, заменить временный пароль. На существующей базе использовать уже установленный пароль.
- [ ] Создать демонстрационные аккаунты VIEWER и MANAGER через панель. Проверочные QA-аккаунты после автоматических проверок удаляются и для защиты не предназначены.
- [ ] Подготовить регистрацию и вход по почте: выполнить OAuth-настройку Gmail по `README.md` и проверить письмо во входящих. Для OAuth consent screen в Testing refresh token действует 7 дней.
- [ ] Пройти [DEFENSE.md](DEFENSE.md): роли, заказ, конфликт версий, фильтры, страницы, архив, заметки, массовые операции, CSV, аналитика, пользователи, аудит, Swagger, миграции.
- [ ] Подготовиться объяснить код и выполнить лайвкодинг: JWT/refresh, BCrypt/OTP, Criteria API, `@Version`, транзакции, Flyway и вычисление приоритета.
- [ ] Передать преподавателю `exports/spin-kr3-submission.zip`. Секретный `.env`, личная база и действующие коды в архив не включаются. Исходники, `.env.example`, инструкции и пример CSV включены.

Отдельный формат пояснительного отчёта в предоставленном тексте задания не указан. Дополнительно удобно сохранить скриншоты health, Swagger и ключевых сценариев защиты. Пиксельное совпадение всех экранов с Figma этой проверкой не подтверждалось; функциональная сверка относится к требованиям КР3.
