# SPIN — контрольная работа №3

Spring Boot REST backend и веб-клиент информационной системы магазина винила. Java 21, Spring Boot 3.5.5, PostgreSQL 17, JPA, Flyway, Spring Security, JWT, Bean Validation, OpenAPI. Клиент перенесён из VINYL_STORE-version_2.1 на React 19 / JavaScript и CSS; Vite собирает его, Spring Boot раздаёт готовый сайт. Исходники — в `frontend/src/`, ресурсы — в `frontend/public/`. Docker собирает обе части автоматически. Android КР №4 сможет использовать тот же JSON API.

## Запуск

Список того, что требуется, что реализовано и что подготовить к защите: [SUBMISSION_CHECKLIST.md](SUBMISSION_CHECKLIST.md). Результаты сверки и исправлений: [AUDIT.md](AUDIT.md).

Запустить Docker Desktop. В корне репозитория:

```bash
python3 scripts/init-env.py
docker compose --env-file .env -f compose.kr3.yml up -d --build --wait
```

Или `bash scripts/start-kr3.sh`; Windows: `powershell -ExecutionPolicy Bypass -File scripts/start-kr3.ps1` (нужен Python 3).

| Назначение | Адрес |
|---|---|
| Магазин | http://localhost:8080/ |
| Панель управления | http://localhost:8080/admin.html |
| Health | http://localhost:8080/actuator/health |
| Swagger (после входа администратора) | http://localhost:8080/swagger-ui.html |
| OpenAPI JSON (администратор) | http://localhost:8080/v3/api-docs |
| PostgreSQL | localhost:55432 / vinyl_store |

`BOOTSTRAP_ADMIN_EMAIL` и случайный временный пароль находятся в локальном `.env`. При первом входе замените временный пароль. Файл не коммитится. Повторный запуск генератора не меняет существующие настройки. Порты задаются в `.env`; скрипты печатают стандартные адреса.

```bash
docker compose --env-file .env -f compose.kr3.yml ps
docker compose --env-file .env -f compose.kr3.yml logs --tail=100 backend
docker compose --env-file .env -f compose.kr3.yml down
```

Обычный `down` сохраняет PostgreSQL в named volume. Для обновления кода повторите запуск с `--build`. Исходные Docker Compose и приложения КР №1–2 продолжают запускаться по прежним инструкциям корневого README.

## Gmail: индивидуальное задание

Пользователь входит по коду из письма; пароль для SMTP и пароли приложений Google не используются. Backend отправляет письма через Gmail API с OAuth 2.0. Отправитель `MAIL_FROM` должен совпадать с Gmail-аккаунтом, которому выданы OAuth-разрешения.

Однократная настройка Gmail:

1. В [Google Cloud Console](https://console.cloud.google.com/) создайте проект и включите Gmail API.
2. Настройте OAuth consent screen как External и добавьте свой Gmail в test users. Создайте OAuth Client ID типа Desktop app.
3. Из корня проекта запустите `python scripts/google-gmail-oauth.py`. Введите Client ID и Client Secret непосредственно в терминале и подтвердите отправку писем в окне Google. Скрипт сохранит OAuth-настройки в локальный `.env`, не выводя токены.
4. Убедитесь, что `MAIL_FROM` в `.env` совпадает с аккаунтом, который вы авторизовали.
5. Пересоздайте backend: `docker compose --env-file .env -f compose.kr3.yml up -d --force-recreate backend`.

При OAuth consent screen в статусе Testing Google отзывает refresh token через 7 дней для Gmail scope; для постоянной работы переведите приложение в Production и выполните требования Google к публикации/проверке. OAuth-секреты хранятся только в игнорируемом Git файле `.env`. Ошибка Gmail возвращает 503. Код не возвращается через API и не печатается приложением.

Если запрос кода возвращает 503, а в логах backend указано `invalid_grant` / `Token has been expired or revoked`, повторно авторизуйте отправителя: запустите `python scripts/google-gmail-oauth.py` из корня проекта и завершите вход Google. Проверьте, что `MAIL_FROM` совпадает с авторизованным Gmail, затем примените новый refresh token: `docker compose --env-file .env -f compose.kr3.yml up -d --force-recreate backend`. Не передавайте содержимое `.env`.

Код: 6 цифр, 5 минут, не более 5 попыток проверки, повторная отправка через 60 секунд, до 5 отправок на адрес в час и до 10 запросов с одного IP в час. Лимит IP хранится в памяти единственного backend и сбрасывается при перезапуске; лимиты адреса и попыток — в PostgreSQL. Новый код заменяет старый. Проверка блокирует строку в БД и исключает двойное использование. Назначения LOGIN и REGISTER разделены. Отключённый или заблокированный пользователь не войдёт по коду. Код не отменяет обязательную смену временного пароля.

Первое посещение: откройте «Регистрация», задайте имя и пароль, запросите код и подтвердите адрес. После этого используйте «Вход» → «Код на Gmail» или «По паролю». Запрос LOGIN для незарегистрированного адреса и REGISTER для уже зарегистрированного возвращает одинаковый ответ без письма: API не раскрывает наличие аккаунта. Если письма нет, проверьте выбранную вкладку, настройки SMTP и папку «Спам».

Проверка обновления сессии на фронтенде: `npm test --prefix frontend`. Защищённые действия, включая смену пароля, обновляют истёкший access-токен через HttpOnly refresh-cookie. Неверный код или пароль при входе не запускает повторную проверку.

## Самовывоз

Покупатель добавляет пластинки в корзину, вводит имя и телефон и подтверждает заказ. Самовывоз бесплатный. Заказ появляется в разделе «Мои заказы» со статусом «Новый».

## Роли

| Роль | Доступ |
|---|---|
| VIEWER | Каталог, оформление корзины, просмотр собственных заказов, аналитика. Без изменения служебных данных |
| MANAGER | Просмотр и изменение всех заказов, архив, заметки, массовые действия, CSV |
| ADMIN | Всё выше, справочник пластинок, пользователи, аудит, Swagger, окончательное удаление |

Регистрация всегда создаёт VIEWER. Администратор назначает роли в панели; пользователь не может передать себе роль в запросе регистрации. Актуальные роли и активность перечитываются из БД для каждого запроса. Администратор не может снять свою ADMIN-роль или отключить себя.

Access JWT хранится в памяти вкладки; refresh — в HttpOnly / SameSite=Strict cookie. Для native-клиента укажите `clientType: "NATIVE"`; refresh возвращается в JSON. При ротации старый refresh отзывается; повторное использование отзывает остальные refresh-сессии пользователя. После выхода access JWT ограничен своим коротким TTL; refresh-сессия отозвана. Смена пароля отзывает все refresh-сессии.

## Данные и API

[Матрица требований](REQUIREMENTS.md), [план](PLAN.md), [сценарий защиты](DEFENSE.md), [проверки](VERIFICATION.md).

Основные маршруты включают `/api/orders`, `/api/records`, `/api/analytics/summary`, `/api/admin/users` и `/api/admin/audit`. Публичный каталог доступен по `/api/catalog`, свои заказы по `/api/shop/orders`, оформление самовывоза по `/api/shop/checkout`.

Пример фильтра: `Pink Floyd пластинка:LP-001 статус:оплачен оплата:да сумма>=3000 приоритет:высокий тег:доставка архив:все`. Русские и английские ключи поддерживаются. Сортировка заказов: `name,asc`, `albumTitle,asc`, `price,desc`, `status,asc`, `updated,desc`; `page` начинается с 0, `size` от 1 до 100. SQL строится Criteria API с параметрами.

Для изменения заказа передавайте `version` из последнего GET; устаревшая версия даёт 409. Для окончательного удаления нужен ADMIN, `PERMANENT_DELETE_ENABLED=true` и заголовок `X-Confirm-Delete: PERMANENTLY_DELETE`.

CSV: UTF-8 с заголовком; экспорт содержит BOM для Excel, импорт поддерживает BOM. Пример — `examples/orders.csv`. Загрузите файл, выберите CREATE_ONLY либо UPSERT_BY_EXTERNAL_ID, нажмите «Проверить», затем «Применить». Apply повторно валидирует файл; корректные строки применяются, ошибочные возвращаются с номером и полем. `invalidRows` считает строки, а не число нарушений. Теги разделяются `|`; цена — рубли. Формулы Excel в экспортируемых текстовых ячейках нейтрализуются.

Сумму в служебном заказе вводит менеджер. При оформлении самовывоза сервер рассчитывает стоимость из актуальных цен со скидками и резервирует нужное количество пластинок.

## Связь с предыдущими КР

Миграция V0 сохраняет исходную структуру `users`, `vinyl`, `orders` с `IF NOT EXISTS`. V1–V3 создают расширенную модель и безопасность, V4 — каталог макета, V5 переносит существующие записи КР №1 в `vinyl_record` и `purchase_order`. UUID вычисляются из прежних ID; `legacy_order_id`, `legacy_customer_id`, `legacy_vinyl_id` сохраняют связи. Исходные таблицы и данные не удаляются. После перехода старые клиенты и новый backend не синхронизируют последующие изменения автоматически.

Чтобы перенести реальные данные, до первого запуска backend восстановите резервную копию таблиц КР №1 в новую базу PostgreSQL или настройте backend на копию исходной базы. Flyway baseline version -1 позволяет применить V0 к непустой базе без таблицы истории. Приложение выполняет миграции один раз. Не запускайте `database.sql` прежнего приложения после миграции: в нём есть DROP TABLE. Старые пользователи-покупатели не превращаются автоматически в аккаунты с паролем; регистрация подтверждает email отдельно.

## Фронтенд версии 2.1

Рабочие исходники магазина находятся в `frontend/src/`, основной CSS — `frontend/src/styles/spin.css`. Старые `static/app.js` и `static/styles.css` заменены React-приложением. Панель `/admin.html` с функциями КР остаётся отдельным клиентом того же backend.

```bash
npm ci --prefix frontend
node scripts/build-frontend.mjs
```

Для этих локальных команд нужен Node.js 22.12+; Docker запускается без установки Node на компьютере. После изменения React-кода при Docker-запуске используйте прежнюю команду с `--build`. Для разработки с быстрым обновлением: `npm run dev --prefix frontend`; Vite проксирует API на backend `localhost:8080`.

Прямые адреса `/catalog`, `/albums/{uuid}`, `/cart`, `/account`, `/orders`, `/favorites`, `/admin` поддерживаются Spring Boot, включая обновление страницы. Неизвестные URL по-прежнему возвращают 404, REST API сохраняет проверку JWT/ролей.

Формы входа и регистрации оформлены как в версии 2.1. Вход доступен по коду на Gmail либо по паролю; регистрация подтверждается кодом. Повторная отправка блокируется на время из ответа сервера. Срок кода — 5 минут. Публичного выбора административной роли нет: роли назначает администратор в панели, как требуется КР.

Каталог, UUID товаров, цены, остатки, учётные записи и заказы используются из PostgreSQL. Пластинка в каталоге вращается автоматически, поддерживает перетаскивание с инерцией, клавиатуру и паузу. Анимации избранного, корзины и появления карточек перенесены из версии 2.1. `prefers-reduced-motion` отключает автоматическое движение.

Бонусные баллы из Python-примера не отображаются: текущий backend не предоставляет бонусную программу. В заказ передаются получатель и телефон; сумму и остаток проверяет Spring Boot. React-страница `/admin` управляет справочником с контролем version и отключением пластинок; CSV, архив заказов, заметки, пользователи и аудит доступны по `/admin.html`.

Готовые `frontend-assets`, `design`, `fonts`, `audio` в `backend/src/main/resources/static/` генерируются сборкой. Не редактируйте их вручную. В архив для сдачи включены первичные ресурсы `frontend/public/`; повторные копии результатов сборки исключены.
